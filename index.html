Travlr Getaways

Full-stack web application · Coursework, enhanced in CS 499 capstone

A full-stack travel application: a customer-facing website for browsing trips, backed by a REST API and MongoDB, plus an Angular single-page application where authenticated administrators can manage trip records.

  • Node.js
  • Express
  • MongoDB
  • Mongoose
  • Angular
  • Handlebars
  • Bootstrap
  • Passport
  • JWT

Repository Capstone-enhanced version

Technical details

The problem

The application started as a static website and grew into a full-stack system in stages — server-rendered pages, then a database layer, then an API, then an admin interface, then authentication. Each stage had to integrate with the previous ones without breaking what already worked.

What I built and improved

  • Built the Express application using an MVC structure, with routes, controllers, and reusable Handlebars views and partials.
  • Designed the MongoDB data layer with Mongoose, including a trip schema with indexed code and name fields and a seed script that restores the original trip data.
  • Built a REST API for trip data (create, read, update, delete) and connected both the customer website and the Angular admin application to it.
  • Added authentication: user registration and login endpoints, passwords stored as salted hashes, and JSON Web Tokens. Write endpoints require a valid token; public read requests do not.
  • During the CS 499 capstone, added Angular route protection for admin pages, reusable server-side validation for trip data, improved API error handling, and corrected HTTP responses.
  • Expanded automated testing to cover validation, authentication input handling, and controller-level behavior — 10 tests, all passing at the end of the capstone.

Engineering takeaway

The most useful lesson was that hiding buttons in the interface is not security: the API itself has to enforce authorization. Testing with Postman confirmed that missing or invalid tokens return 401 Unauthorized while public reads still work.

Grazioso Salvare Rescue Animal Dashboard

Python & MongoDB · Coursework, enhanced in CS 499 capstone

A Python dashboard that connects to a MongoDB database of animal shelter records and helps identify animals suited to search-and-rescue work. Users filter records by rescue profile — water rescue, mountain or wilderness rescue, and disaster or individual tracking — and review results in a data table, a breed visualization, and a geolocation map.

  • Python
  • Dash
  • MongoDB
  • PyMongo
  • unittest
  • Jupyter

Repository Enhanced version Original version

Technical details

The problem

The original dashboard worked, but its database layer had real weaknesses: credentials were hard-coded in the source, breed summaries were computed in the application instead of the database, and there was no protection against invalid or overly broad database operations.

What I built and improved

  • Built the reusable Python CRUD module and the Dash dashboard that retrieves, filters, and visualizes shelter records.
  • During the CS 499 capstone, replaced hard-coded credentials with environment-based configuration and added ignore rules so local credential files are never committed.
  • Added a compound MongoDB index on the fields most often used together in rescue queries (animal type, breed, sex, and age).
  • Moved breed-summary processing into the database with an aggregation pipeline ($match, $group, $sort, $limit), instead of summarizing in Pandas after retrieval.
  • Added input validation, blocked unrestricted update and delete operations caused by empty queries, and improved error handling so the application does not expose unnecessary database information.
  • Wrote a 12-test automated suite using Python unittest with mocked MongoDB objects, covering the enhancements and existing CRUD operations — all 12 tests passed.

Engineering takeaway

Small implementation decisions carry outsized risk: a hard-coded credential or an unguarded delete is easy to write and expensive to miss. The work also showed how much database design matters — the right index and the right place to run a summary change both performance and reliability.

Software Test Automation

Java & JUnit · Coursework

A contact-management service built to be tested: a Contact model that enforces its own validation rules, and a ContactService that stores, retrieves, updates, and deletes contacts — each covered by JUnit tests.

  • Java
  • JUnit

Repository

Technical details

What I built

  • Validation rules in the model for field lengths, required values, and unique contact IDs, with invalid input rejected by exceptions rather than silently accepted.
  • Service operations for adding contacts, rejecting duplicate IDs, deleting contacts, and updating fields.
  • JUnit tests that verify the rules and the service behavior, including edge cases such as duplicate IDs and invalid updates.

Course Planner

C++ · Coursework, enhanced in CS 499 capstone

A C++ console application that loads course data from a CSV file, prints courses in alphanumeric order, and looks up a course to show its details and prerequisites.

  • C++17
  • Hash tables
  • Binary search trees
  • Graphs
  • Topological sort

Repository Capstone-enhanced version

Technical details

What I built and improved

  • Original: a hash table for fast course lookup and a binary search tree for sorted traversal, with CSV parsing, file I/O, and a menu-driven interface.
  • Capstone enhancement: added a PrerequisiteGraph class that models prerequisite relationships as a directed graph (adjacency list with indegree tracking) and uses Kahn's topological sorting algorithm — O(V + E) — to produce a valid order for completing courses.
  • Added cycle detection for circular dependencies and validation that reports references to courses missing from the dataset, each handled separately.
  • Verified the enhancement with manual tests covering normal ordering, circular dependencies, and missing prerequisites — all produced the expected results.

Engineering takeaway

Choosing the right data structure changed what the application could do: a hash table and a tree could store and display courses, but only a graph could reason about the relationships between them.
